业务/任务分析BUSINESS & TASK ANALYSIS

业务分析回答"这门生意为什么值得做"，任务分析回答"为了做成它，人和系统每天到底要干哪些活"。两者合起来构成 BRS 的问题域输入，也是后续每一条相关方需求的出处。

业务背景：四个环节之间的断裂CONTEXT

康复与辅助器具业务的基本链路是"评估—处方—训练—复评"。问题不在环节缺失，而在环节之间的信息断裂：评估依赖量表与治疗师观察，处方依赖经验，训练发生在治疗室内的有限时段，复评往往要等下一次门诊。患者回到家里之后，训练做了什么、做了多少、做得好不好，临床上基本不可见。神经接口类设备本可以补上这段数据，但多数产品把信号留在设备里，没有回流到临床决策，形成了"设备能用、业务不通"的局面。

另一个断裂发生在辅助环节本身。传统义肢与外骨骼是被动执行器：人给指令，机器执行，人不接收机器的反馈。把意图解码与感觉反馈接进来之后，辅助才从"替人做"变成"与人一起做"，但随之而来的是安全责任、数据责任和临床责任的新界面——这三类责任必须在业务层先定义清楚，否则系统做得再精细也无法交付。

典型任务流：从处方到复评

T4 处方配置→ T5 居家训练→ T6 监护与处置→ T7 数据回传→ T7 复评→ T4 处方调整

这条流每循环一次，构成一个"训练周期"。系统的时间常数应当是"天"，而不是"次门诊"——这是 O3 与 BR-03 的来源。

运营概念 ConOpsCONCEPT OF OPERATIONS

ConOps 是组织视角的叙事：一家医院、一个社区康复站或一个家庭，怎样把这套系统嵌入现有的班次、角色和流程里，用它在真实环境中完成使命。它描述"谁—何时—何地—做什么—靠什么协同"，不描述系统内部的模式与时序。

使用情境与运行环境CONTEXTS

同一套系统在四种环境里的约束完全不同：医院有稳定的电源与网络、有专业人员在场，但空间拥挤、患者周转快；家庭有充足的佩戴时长，但网络、照明、照护者能力都不稳定；社区与户外则把安全边界推到最大。场景设计必须覆盖这四种环境的最差组合，而不是按最好的那种设计。

ENV-1 / 医院康复科
高强度、短周期、强监督

患者在治疗师视线内训练 30–60 分钟，设备每日多患者轮用，要求快速消杀与快速换人；网络与电源稳定，数据需当日进入病历。

ENV-2 / 社区康复站
中等强度、弱专业支持

由康复指导员协助，专业判断能力弱于医院；设备数量少、维护半径大，故障必须能远程定位。

ENV-3 / 家庭
长时间佩戴、弱网、照护者非专业

每日佩戴数小时，训练与日常生活混在一起；网络时断时续，夜间告警必须本地可见、可听、可触达。

ENV-4 / 社区与户外
移动、不可预测、安全优先级最高

地面材质变化、人流、上下台阶、强光与噪声都会干扰信号与反馈可辨识度；跌倒风险与设备脱落风险同时上升。

运营场景OPERATIONAL SCENARIOS

六个场景覆盖"配置—日常—随行—复评—应急—退役"的完整运营周期。每个场景都写明触发条件、主流程、异常分支与后置状态；异常分支不是附注，它是安全类需求的主要来源。

S1 · 首次 90 分钟 / 医院
入组与基线标定

触发　门诊评估通过并签署知情同意。
主流程　基线量表与运动功能评估 → 电极点位选择与阻抗检查 → 静息与最大自主收缩采样 → 阈值与分类器标定 → 试戴验收与宣教。
异常　阻抗不达标则更换点位重测；标定不收敛则回退保守默认参数并标记"待复标"。
后置　基线档案、设备配置版本 v1、患者端账号就绪。
承接　T1–T4，StR-RT-01 / RT-03 / PT-05

S2 · 每个训练日 / 家庭
居家训练闭环

触发　患者按计划开机，或治疗师推送了新任务。
主流程　佩戴自检（阻抗、电量、时基）→ 任务引导与动作示范 → 多组闭环辅助训练（组间休息）→ 训练后小结（完成率、辅助占比、主观用力）→ 本地留存并在联网时回传。
异常　自检不通过引导重戴；置信度持续偏低转监护模式；患者不适立即暂停并记录。
后置　训练记录入库，次日计划微调。
承接　T5，StR-PT-05 / PT-06 / RT-01 / RT-02

S3 · 白天不定时 / 社区与户外
随行辅助

触发　患者主动开启辅助，或按场景预设自动切换。
主流程　场景选择（平地 / 上下楼 / 坐站 / 抓握）→ 连续意图解码与助力输出 → 感觉反馈按接触强度分级 → 疲劳与姿态监测 → 结束回传当日累计。
异常　检测到跨越障碍或跌倒风险时提升刚度并语音提示；连续过载时限幅并降级。
后置　辅助日志与疲劳指数更新。
承接　T5–T6，StR-PT-03 / PT-04 / PT-06

S4 · 每 1–2 周 / 治疗师工作站
随访复评

触发　周期到达，或指标异常触发提醒。
主流程　打开趋势视图（依从率、辅助占比、异常事件）→ 与基线及上次对比 → 调整处方或参数（草稿→确认）→ 推送患者端 → 生成复评摘要写入病历。
异常　数据缺失时标注缺失原因而不臆测趋势；参数冲突阻断并要求临床确认。
后置　新处方版本与复评记录。
承接　T7，StR-RT-02 / RT-03 / RT-05 / MD-01 / MD-02

S5 · 夜间 / 家庭
异常与应急

触发　跌倒、电极脱落、刺激过流、心率异常，或患者主动呼救。
主流程　系统分级判定（关注 / 处置 / 紧急）→ 紧急级立即切断输出并本地声光提示 → 通知照护者与家属 → 按预案呼叫急救并上报位置与状态 → 事件留痕待复盘。
异常　网络中断时本地告警并用短信/电话兜底；误报可一键取消并标注样本。
后置　事件报告，设备停留在安全状态等待确认。
承接　StR-CG-01 / CG-03 / EMR-01 / REG-01

S6 · 季度或按需 / 机构
维护、升级与退役

触发　版本发布、故障码上报、寿命计数到限，或患者退出。

生命周期阶段LIFE CYCLE

ConOps 不只看"用起来的时候"。部署、支持与退役同样消耗相关方的时间与信任，也最容易在需求阶段被漏掉。

阶段 1
开发与设计确认厂商主导，临床与患者代表参与评审；产出可验证的原型与安全论证，机构不承担使用风险。
阶段 2
部署与配置现场工程师安装、管理员建账、治疗师完成首例标定；目标单套 ≤2 h，且不依赖厂商常驻。
阶段 3
日常使用患者在家庭与社区中训练与随行辅助，照护者响应告警，治疗师按周期复评；系统的时间常数是"天"。
阶段 4
支持与维护远程诊断、备件更换、分阶段升级与模型校准；故障定位要到子系统/模块粒度，避免整机返厂。
阶段 5
退役与数据清除导出个人数据、彻底清除设备内数据、回收含植入件的处置路径；清除需留下可审计证明。

运行模式与状态迁移MODES & TRANSITIONS

八种模式的设计原则只有一条：任何不确定都退到输出更少的那个状态。模式不是界面皮肤，而是软件与硬件的联合状态——每个模式都明确允许做什么、禁止做什么，以及谁能把它迁出去。

迁移触发条件迁移动作与约束
M0 → M1上电 / 复位执行上电自检（电极阻抗、电池、时基、存储），≤10 s；自检期间输出回路物理断开
M1 → M2首次使用、配置变更、重戴后进入标定，驱动端机械锁止；标定结果写入配置版本
M1 → M3自检通过、未开启辅助默认落在监护态——这是系统的安全基态
M2 → M3标定收敛且阻抗达标加载参数，进入监护；未收敛则保持保守默认参数并标记待复标
M3 → M4患者开启辅助，且置信度与阻抗均达标启用完整闭环；安全系统开始逐周期监视
M4 → M3患者关闭辅助 / 训练任务结束平滑撤力，避免突然失去支撑
M3 / M4 → M5阻抗漂移、置信度持续低、电量 <15%、链路中断限幅或仅监护，明确告知用户能力已下降
M5 → M3条件恢复且自检通过逐步恢复能力，不做一次性跳变
任意 → M6急停按钮、过流、跌倒判定、主动呼救硬件切断输出回路，仅保留采集与告警；需人工复位
M6 → M1人工复位复位后必须重跑自检，不复用故障前参数
M3 → M7维护指令，且患者不在训练中关闭输出，允许升级与数据导出
M7 → M1升级完成或失败回滚强制自检；失败自动回到上一稳定版本
